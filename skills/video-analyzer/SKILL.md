# Video Analyzer

Локальный анализ видео для продакт-менеджера. Принимает **путь к файлу** или **YouTube-ссылку**,
извлекает кадры и речь полностью локально (ffmpeg + WhisperX, без облака), и выдаёт анализ,
адаптированный под жанр видео.

## Жанры (выбирай стратегию под жанр)

| Жанр | Признаки | Фокус анализа |
|---|---|---|
| **Созвон / интервью** | локальный файл, несколько говорящих, диалог | речь: транскрипт + диаризация → продуктовое саммари |
| **Демо инструмента / конкурента** | чаще YouTube, один голос/закадр, показ экрана | **визуал**: кадры → разбор продукта (это не диалог) |
| **Гибрид** | созвон, где клиент шарит экран | связать «что говорит» с «что показывает» |

## Workflow

### 0. Проверка зависимостей (один раз)
```bash
command -v ffmpeg >/dev/null && command -v yt-dlp >/dev/null && [ -d "$SKILL_DIR/.venv" ] \
  && echo OK || echo "RUN: bash $SKILL_DIR/scripts/setup.sh"
```
Если не OK — предложи запустить `bash $SKILL_DIR/scripts/setup.sh` (поставит ffmpeg/yt-dlp и whisperx,
спросит токен HuggingFace для диаризации).
Для PDF-отчёта нужны ещё `pandoc` и `weasyprint` (brew) — проверь `command -v pandoc weasyprint`.

### 1. Рабочая папка (временная, безопасная)
```bash
WORK="$(mktemp -d)" && chmod 700 "$WORK" && echo "$WORK"
```

### 2. Получить видео (URL или локальный файл)
```bash
VIDEO="$(bash "$SKILL_DIR/scripts/ingest.sh" "<URL-или-путь>" "$WORK" | tail -1)"
```

### 2b. Решить: всё видео или отрезок (фокус-режим)
Перед извлечением определи длительность и выбери охват. **Не спрашивай без нужды** — лишний вопрос
на коротком ролике раздражает.
```bash
DUR_MIN=$(( $(ffprobe -v quiet -show_entries format=duration -of csv=p=0 "$VIDEO" | cut -d. -f1) / 60 ))
```
Правило выбора:
- **Пользователь уже назвал отрезок** («первые 5 минут», «с 35-й минуты», «последние 2 минуты»,
  «момент про X на 12:30») → бери его, **не спрашивай**, выставь `FOCUS_START`/`FOCUS_END`.
- **Видео короткое (≤ ~15 мин) и отрезок не назван** → разбирай **целиком**, не спрашивай.
- **Видео длинное (> ~15 мин) и отрезок не назван** → спроси через `AskUserQuestion`: смотреть всё
  или конкретный фрагмент. Поясни, что по фрагменту разбор точнее и быстрее (кадры гуще, транскрипт
  только по окну). Варианты: «Всё видео», «Указать отрезок» (тогда уточни тайминги), при необходимости
  «Только первые N минут». Если пользователь выбрал отрезок — переведи в `FOCUS_START`/`FOCUS_END`.

Сохрани выбор в переменные окружения для шага 3 (пусто = всё видео):
```bash
# пример, если выбран отрезок:
FOCUS_ENV=(FOCUS_START=35:00 FOCUS_END=38:00)   # иначе FOCUS_ENV=()
```

### 3. Извлечь кадры (анализ → план) и аудио
```bash
bash "$SKILL_DIR/scripts/extract.sh" "$VIDEO" "$WORK"
# → $WORK/audio.wav, $WORK/frames/frame_XXXX.jpg, $WORK/frames/timestamps.txt, $WORK/analysis.txt
```
Кадры берутся по схеме **«анализ → план»**: сначала дёшево размечается структура (карта смен сцены +
интервалы тишины, без записи кадров), затем `scripts/plan_frames.awk` строит план — **кадр на каждую
смену сцены** (события: переключения UI/слайдов) плюс **редкий добор в длинных статичных «дырах»**
(тишина → 1 кадр; речь над статикой → раз в ~30с), всё в пределах бюджета `MAX_FRAMES`. Так на демо
кадры густеют там, где меняется экран, а на «говорящей голове» не тратятся на статичное лицо.
`timestamps.txt` даёт таймкод каждого кадра; `analysis.txt` — сводку (число сцен, интервалов тишины,
кадров в плане, формат кадров), её можно учесть при определении жанра (шаг 4).

**Формат кадров (важно для демо/скринкастов).** По умолчанию кадры — `jpg` (компактно). Для
**демо/скринкастов/слайдов**, где надо читать мелкий текст UI, ставь `FRAME_FORMAT=png` (без потерь —
jpeg «мылит» мелкий шрифт). Для **созвонов/говорящих голов** оставляй `jpg`. Выбранный формат
пишется в `analysis.txt` (`frame_format=`), а кадры получают соответствующее расширение
(`frame_XXXX.png`).
```bash
FRAME_FORMAT=png bash "$SKILL_DIR/scripts/extract.sh" "$VIDEO" "$WORK"   # демо/скринкаст
```

**Фокус-режим (разбор отрезка видео).** Когда на шаге 2b выбран отрезок — задавай окно через env
`FOCUS_START` / `FOCUS_END` (форматы `SS`, `MM:SS`, `HH:MM:SS`; можно только `START` = «до конца»,
только `END` = «с начала»):
```bash
FOCUS_START=35:00 FOCUS_END=38:00 bash "$SKILL_DIR/scripts/extract.sh" "$VIDEO" "$WORK"
```
Кадры **и** аудио режутся по окну: на 3 минутах те же `MAX_FRAMES` дают в разы гуще покрытие, чем
размазанные по часу, а локальный whisper транскрибирует только окно (намного быстрее на длинных
записях). Таймкоды кадров и транскрипта остаются **абсолютными** (реальная шкала видео) — `extract.sh`
прибавляет смещение и пишет его в `$WORK/focus_offset`, а `transcribe.sh` (шаг 5) подхватывает файл
сам и сдвигает SRT/JSON/TXT. Ничего дополнительно передавать в transcribe не нужно. Для длинного
видео фокус по нужному отрезку гораздо полезнее разреженного прохода по всей записи.

### 4. Определить жанр
Эвристика → озвучь предположение пользователю, дай поправить:
- источник YouTube + мало речи/один голос → **демо**;
- локальная запись, много кадров-переключений + речь → **гибрид**;
- локальная запись, мало кадров, диалог → **созвон**.

### 5. Транскрибировать (для созвона/гибрида; для чистого демо — опционально)
```bash
# созвон/гибрид с метками говорящих:
bash "$SKILL_DIR/scripts/transcribe.sh" "$WORK/audio.wav" "$WORK" diarize ru
# демо без диалога (или если речь — просто закадровый комментарий):
bash "$SKILL_DIR/scripts/transcribe.sh" "$WORK/audio.wav" "$WORK" plain ru
```
Транскрипт с таймкодами/метками: `$WORK/audio.srt`, `$WORK/audio.txt`, `$WORK/audio.json`.
Метки `SPEAKER_00/01...` сопоставь с ролями (клиент/интервьюер/PM) по контексту разговора.
Дополнительно пишутся: `$WORK/audio.json` — сегменты-фразы с таймкодами (в монологе теперь
не один блок, а нормальные фразы ~2.5с); `$WORK/audio.words.json` — пословный тайминг с
уверенностью (`prob`), источник истины (нужен шагу 5b и редактору Transcript Editor).

**Глоссарий → подсказка Whisper (если есть).** Если для этого видео/проекта уже есть глоссарий
Transcript Editor (`projects/<slug>/glossary.json` проекта и/или глобальный `glossary.json` рядом
с корнем проектов) — передай его: whisper заметно точнее пишет названия продуктов, имена и жаргон.
```bash
GLOSSARY_JSON=/путь/к/projects/<slug>/glossary.json \
  bash "$SKILL_DIR/scripts/transcribe.sh" "$WORK/audio.wav" "$WORK" diarize ru
# либо подсказка вручную: WHISPER_PROMPT="Словарь терминов: REES46, Starter." bash …
```

### 5b. Отобрать ценные кадры (дедуп → контактные листы → скринер)
`extract.sh` извлекает ЩЕДРО (кадр на каждый показ, потолок `EXTRACT_MAX`=300). Ценность и
дубли по самим кадрам судим content-aware, экономя токены (см. `DESIGN_frame_selection.md`):

```bash
python "$SKILL_DIR/scripts/dedup_frames.py"   "$WORK"   # near-identical → _kept.tsv (CPU, 0 токенов)
python "$SKILL_DIR/scripts/contact_sheets.py" "$WORK"   # _sheet_NN.png (сетка тамбнейлов) + _sheet_index.tsv
```
Затем **запусти субагент(ы)-скринер** (Agent tool) на листах `$WORK/_sheet_*.png` — он читает
ОДНУ картинку вместо десятков тамбнейлов (дёшево, вне твоего контекста) и возвращает, какие
номера кадров ценны. Промпт скринера (по одному листу или всем сразу):

> Тебе даны контактные листы — сетки пронумерованных тамбнейлов (в левом верхнем углу зелёный
> НОМЕР кадра + таймкод). Read каждый лист. Для КАЖДОГО номера классифицируй: **UI** (виден
> интерфейс/экран/приложение/планшет/монитор/карта — ЦЕННО), **venue** (интерьер/оборудование
> без экрана — иногда ценно), **talking-head** (просто ведущий — НЕ ценно), **transition**
> (смаз/пустой — НЕ ценно). Правила keep: бери ВСЕ уникальные UI; venue — если показывает новое;
> НЕ бери talking-head/transition; из дублей одного экрана оставь один (остальные dup_of); при
> СОМНЕНИИ — бери. Верни таблицу `idx | category | keep | dup_of | одностроч. описание` и строку
> `KEEP: <номера через запятую>`.

Много листов (длинное видео) → несколько скринеров параллельно, потом слить KEEP; при
переполнении бюджета `MAX_FRAMES` — второй лист из survivors и финальный отбор.
Сопоставь номера из `KEEP` с файлами кадров по `$WORK/_sheet_index.tsv` — это **финалисты**.

### 5c. Контекст речи для финалистов (скаффолд)
```bash
python "$SKILL_DIR/scripts/frame_windows.py" "$WORK" > "$WORK/_frames_scaffold.md"
```
По каждому кадру — сегменты речи из его временно́го окна (`CTX_LEAD`/`CTX_FLOOR`/`CTX_CAP` = 5/8/90с).

### 6. Прочитать ФИНАЛИСТЫ (полное разрешение) и собрать `frames_context.md`
`Read` **только кадры-финалисты** (из `KEEP`) в полном разрешении — здесь тонкие текстовые
различия, которые тамбнейл мог не передать, видны точно (Read читает JPG/PNG как изображение;
расширение — из `frame_format` в `analysis.txt`). Возьми их контекст речи из `_frames_scaffold.md`,
**сам по смыслу** склей сегменты в законченные мысли (границы Whisper рвут фразы — соединяй;
явный бред ASR правь, но не додумывай) и запиши `$WORK/frames_context.md`: по кадру — «что на
экране» + «контекст речи» с таймкодами (и ролью для созвона). Это источник для отчёта и подписей.

**Охват (важно для демо — цель ≥80% полезных экранов):** финалисты должны покрыть ВСЕ уникальные
интерфейсы. Сверься с транскриптом: если модуль/экран назван в речи, а скриншота нет — значит он
не извлёкся или скринер счёл дублем; **догони фокус-режимом** нужный отрезок (см. «Покрытие
кадров»), затем добавь. Не описывай интерфейс без скриншота и не выдумывай его.

### 7. Синтез — вывод по жанру (см. ниже)
Сохрани полный транскрипт рядом с источником: `<имя-видео>.transcript.md`
(таймкоды + метки говорящих). Затем выдай саммари.

### 7b. Собрать PDF-отчёт (ПО УМОЛЧАНИЮ для любого жанра — созвон, демо, гибрид)
После разбора **всегда** собирай PDF (не только для созвона). Шаблон зависит от жанра
(см. «Формат: PDF-отчёт»): для созвона — диалог по ролям, для демо — слайды + разбор без диалога.
```bash
# 1) ключевые кадры → постоянная папка (НЕ temp), переименуй осмысленно.
#    ВАЖНО: бери реальное расширение кадров (jpg/png — см. шаг 6), а не хардкодь .jpg.
#    Проверь имя выбранного кадра (Read), затем копируй именно его — нумерация кадров
#    меняется при каждом извлечении, не полагайся на номер «по памяти».
mkdir -p "$OUTDIR/assets" && cp "$WORK/frames/frame_00NN.png" "$OUTDIR/assets/<имя>.png"
# 2) сохрани контекст кадров рядом с отчётом (инспектируемый артефакт):
cp "$WORK/frames_context.md" "$OUTDIR/frames_context.md"
# 2b) (только созвон/гибрид) черновик диалога из размеченного SRT:
python "$SKILL_DIR/scripts/srt_to_dialogue.py" "$WORK/audio.srt" > "$OUTDIR/_dialogue_draft.md"
# 3) модель пишет $OUTDIR/report.md по шаблону жанра, затем:
bash "$SKILL_DIR/scripts/make_report.sh" "$OUTDIR/report.md" "$OUTDIR/assets" "$OUTDIR/<имя>.pdf"
```

### 7c. Предложить импорт в Transcript Editor (если он установлен)
Если рядом с проектами есть Transcript Editor (веб-редактор транскрипта: клик по слову → видео,
правка слов/спикеров, глоссарий) — **предложи** пользователю импортировать разбор (не делай молча).
**Строго ДО шага 8**: импортёр копирует `audio.words.json`/`audio.json` из `$WORK`.
```bash
python <transcript-editor>/server/importer.py --video "$VIDEO" --analysis "$WORK" --title "<название>"
```

### 8. Очистка
```bash
rm -rf "$WORK"
```
(Не удаляй сохранённый транскрипт, `frames_context.md`, постоянную папку `assets/` и собранный
PDF/отчёт. Если пользователь хотел редактировать транскрипт — сначала шаг 7c, потом очистка.)

## Переанализ с правками из Transcript Editor (corrected + глоссарий + контекст)

Когда пользователь просит **пересобрать отчёт с учётом правок** («пересобери с моими правками»,
«обнови отчёт», «analysis stale») — источником истины становятся артефакты редактора, а не сырой
выход пайплайна.

1. **Найди проект редактора**: каталог `projects/<slug>/` с `project.json`, где `source_video`
   указывает на это видео (или пользователь назовёт проект сам).
2. **Возьми правленые файлы** из каталога проекта:
   - `audio.corrected.json` — сегменты с **финальными** именами спикеров и правленым текстом
     (формат тот же, что у `audio.json`);
   - `transcript.corrected.md` — человекочитаемый диалог с таймкодами: **готовый черновик**
     расшифровки по ролям (заменяет `srt_to_dialogue.py`);
   - `context.md` — вводная от пользователя (участники, цель созвона, продукт) — прочитай и
     учитывай при синтезе, не переспрашивай то, что там уже сказано;
   - `glossary.json` (+ глобальный рядом с корнем проектов) — термины пиши каноничным написанием,
     `note` терминов используй как знание о продукте.
   Если corrected-файлов нет или они старее `edits.json` — попроси нажать «Экспорт: транскрипт
   для переанализа» в редакторе, либо (если сервер запущен) сам:
   `curl -X POST localhost:8787/api/projects/<slug>/corrected`.
3. **Не переделывай работу пользователя**: имена спикеров в corrected — финальные (не
   восстанавливай роли заново и не переименовывай); цитаты бери из правленого текста, не из
   сырого SRT. Кадровую часть не пересобирай, если `frames_context.md` и `assets/` сохранились
   с прошлого прогона — переанализ обычно только про текст.
3b. **Кадры пользователя (`frames.json` проекта редактора).** Прочитай `frames.json`: кадры с
   `source: "user"` пользователь добавил сам (снял с видео или загрузил) — они **ОБЯЗАТЕЛЬНЫ**
   в отчёте. Его `caption` — ОСНОВА подписи-связки: смысл не переписывай, можно дополнить
   контекстом речи в этот момент; кадр без caption подпиши сам по правилу подписи-связки.
   Файлы лежат в `frames/` каталога проекта — копируй в `assets/` как обычно. Кадры
   `source: "skill"` (или без поля) — по усмотрению, как всегда.
4. **После сборки PDF сними флаг устаревания** в `projects/<slug>/project.json`: проставь
   `analysis.report_path`, `analysis.generated_at` (UTC ISO) и `analysis.stale = false`.

## Форматы вывода

### Саммари — созвон / интервью
Контекст пользователя: PM, ведёт Discovery и анализирует работу бизнес-аналитиков и других продактов.
- **Участники и роли** (по диаризации + контексту)
- **Темы** разговора
- **Боли / потребности / задачи клиента** — с цитатами и таймкодами
- **Ключевые решения и договорённости**
- **Action items** (кто / что / когда, если прозвучало)
- **Открытые вопросы и упущенные зацепки**
- **Оценка качества интервью**: открытые vs наводящие вопросы, давали ли клиенту говорить,
  что стоило доспросить (полезно для разбора работы бизнес-аналитика)

> **Критический разбор** (ниже) — отдельный **опциональный** блок поверх саммари. По умолчанию его
> НЕ делаем; включаем только по явному запросу пользователя.

#### Критический разбор (ОПЦИОНАЛЬНО — по умолчанию ВЫКЛЮЧЕН)
Эпистемический разбор речи по мотивам `transcript-critic`: разложить, **на чём стоят заявления** и где
их слабые места. Наше преимущество — **диаризация**: где есть роли, привязываем каждый пункт к роли
И таймкоду; в монологе роль одна — «Автор».

**Когда включать:** ТОЛЬКО если пользователь явно просит — «разбери критически / оцени качество
интервью / разбери работу аналитика / насколько обоснованно». В обычном разборе и саммари **не делай
и не предлагай**. Для чистой UI-проходки демо неуместно (нет заявлений); для созвонов и для
докладов/питчей с содержательными заявлениями — по запросу уместно.

**Определи форму** (она задаёт, какие части писать; форму можно назвать в чате, но в ОТЧЁТ это не выноси):
- **Диалог** (несколько говорящих) → доказательная база **+ интервью-части**.
- **Монолог** (один спикер) → доказательная база **+ монолог-части**.

**Принципы (соблюдай строго):**
- **Неприменимое — молча опусти.** Пиши только подходящие части. **НИКАКИХ пометок «неприменимо /
  N/A / это монолог, поэтому…»** в отчёте — просто не включай эту секцию. Читателю не нужно знать,
  чего ты НЕ написал.
- **Только по содержанию транскрипта.** Не привлекай внешние знания о спикере/продукте, не домысливай.
- **Каждый пункт — роль + таймкод** («[Клиент · 12:30]» / «[Автор · 04:30]»). Не уверен по говорящему — оговори.
- **Нейтрально:** описывай, не осуждай. **Только значимое:** что реально влияет на выводы; придирки — нет.

**Общая часть (всегда) — На чём стоят заявления (доказательная база).** Для ключевых утверждений укажи
тип опоры: *Личный опыт/практика* («у нас на практике…») · *Мнение/гипотеза* («кажется, было бы
удобно…» — не факт) · *Данные/факт* (цифры, конкретный случай) · *Вещественное подтверждение*
(показанный артефакт — демо, лог, скрин — сильнейший довод) · *Чужое мнение/авторитет* («коллеги/
эксперт говорят…» — из вторых рук, особенно без источника) · *Аналогия* (иллюстрация, не доказательство).

**Интервью-части (только диалог):**
- **1д. Что стоило доспросить.** Где боль названа, но не измерена; гипотеза не проверена примером;
  ушли от темы; интервьюер не копнул. С таймкодом.
- **2д. Качество ведения.** Открытые vs наводящие вопросы (наводящий подсказывает ответ: «вам же
  неудобно, что…?»); давали ли собеседнику говорить (баланс речи); слабые ходы — поспешное обобщение,
  выводы за собеседника. Чисто — так и напиши.

**Монолог-части (только монолог):**
- **1м. Перехайп / сильные заявления.** Где формулировка сильнее показанного («полностью автономно»,
  «идеально», «×200%») и чем именно не подкреплена в самом материале. С таймкодом.
- **2м. Промо-уклон / конфликт интересов** (нейтральная пометка). Продажа курса/сообщества/продукта,
  спонсор, ссылка-CTA — не делает заявления ложными, но их стоит читать с этой поправкой.
- **3м. Что недораскрыто / логические пробелы.** Опущены стоимость/риски/частота отказов; авторитетные
  ссылки без источника; вывод не следует из показанного. С таймкодом.

### Саммари — демо инструмента / конкурента (визуальный анализ)
- **Что за продукт и для кого**
- **Ключевые экраны / фичи** — со ссылками на кадры и таймкоды
- **UX-флоу и паттерны**; что выделяет продукт
- **Выводы для нас**: чему поучиться, чего избегать

**Покрытие кадров (важно для слайд-видео/демо):** `extract.sh` планирует кадры по структуре
(кадр на каждую смену сцены + редкий добор в статичных «дырах» — см. шаг 3), поэтому уникальные
экраны обычно покрыты. **Прочитай КАЖДЫЙ уникальный слайд/экран, а не выборку** — почти-дубли (один и тот же слайд)
пропускай, но не пропускай слайды с новым содержанием. Сверяйся по номерам слайдов (если видны):
пропуск в нумерации = есть непрочитанный слайд, вернись и прочитай его. Не объявляй «больше
смысловых кадров нет», пока не прошёл все уникальные экраны.

**Если этап есть в речи, но экрана к нему нет** (частый случай: интерфейс показывают недолго
под говорящей головой — порог смены сцены не срабатывает и кадр не извлекается). Не описывай
такой этап без скриншота и не выдумывай — **догони кадры фокус-режимом** по этому отрезку:
`FOCUS_START=<нач> FOCUS_END=<кон> ANALYZE_THRESH=0.06 bash scripts/extract.sh <video> <focus_work>`
(порог ниже → ловит и слабые переходы), затем прочитай новые кадры и добавь недостающий экран.
Границы отрезка бери по таймкодам из `frames_context.md`/транскрипта вокруг пропущенной темы.

**PDF по умолчанию (демо):** после разбора собери PDF (`make_report.sh`) по демо-шаблону —
обложка + разбор простым языком + слайды. Диалога по ролям тут нет (это закадр одного-двух
ведущих), вместо него — связный текст. Транскрипт закадра (`plain`) можно процитировать в выводах.

**Скриншоты — ВНУТРИ текста, рядом с выводом, который они подтверждают** (а НЕ списком в конце).
Каждый скриншот ставь сразу под тем абзацем/пунктом, который он иллюстрирует, с подписью-связкой
(«вот этот экран показывает, что…»). Один вывод — один-два подтверждающих кадра. Так читатель
видит аргумент и доказательство вместе. Финального раздела-свалки «Скриншоты» быть не должно.

**Как писать подпись (правило подписи-связки):** подпись — это твой СИНТЕЗ, а не цитата. Опирайся
одновременно (1) на то, что сам видишь на кадре, и (2) на «контекст речи» этого кадра из
`frames_context.md` — что говорилось в этот момент. **Не вставляй дословную реплику из транскрипта
за этот промежуток**: речь используй лишь как подсказку о смысле/намерении («что именно показывают
и зачем»), а формулируй своими словами, понятным языком. Цель подписи — объяснить, почему кадр
здесь и что из него следует, а не пересказать сказанное. Если речь и картинка расходятся (кадр на
переходе, закадр уже про следующее) — доверяй тому, что НА кадре, речь оставляй фоном.

### Гибрид
Саммари созвона + врезка «**Что показали на экране**» по сегментам шаринга (кадр + что говорилось).
Врезку строй из `frames_context.md`. Подпись к кадру — это твой СИНТЕЗ: опирайся и на то, что сам
видишь на кадре, и на контекст речи этого кадра как подсказку о смысле/намерении, но **не вставляй
дословную реплику из транскрипта** — формулируй своими словами, понятным языком. Если речь и картинка
расходятся (кадр на переходе, речь уже про следующее) — доверяй тому, что НА кадре, речь оставляй фоном.

### Формат: PDF-отчёт (главный осязаемый артефакт, по умолчанию для любого жанра)
Собирается через `scripts/make_report.sh` (pandoc + weasyprint). Цель — чтобы отчёт читал любой
человек без погружения в продукт. Ниже подробно шаблон **созвона**; для **демо** — упрощённый
шаблон в конце раздела (без диалога). Три обязательных части для созвона/гибрида:

1. **Выводы понятным языком, без терминов и усложнений.** Пиши как для коллеги не из темы:
   объясняй механику простыми словами («система ждёт 10 минут, потом проверяет, заказал ли
   человек»), а не ярлыками (никаких «frequency cap / дедуп / атрибуция / gap» — если термин
   нужен, тут же расшифруй обычными словами). Структура свободная, но обычно: «О чём видео» →
   разбор по простым шагам → «Главное» → «Что нового / что уже знали».
2. **Скриншоты** ключевых экранов (кадры из сегментов шаринга) — **встроены рядом с выводом,
   который подтверждают** (не отдельным списком), с короткими понятными подписями-связками.
   Подпись — твой СИНТЕЗ: опирайся и на то, что сам видишь на кадре, и на контекст речи этого кадра
   из `frames_context.md` как подсказку о смысле, но **не вставляй дословную реплику из транскрипта** —
   формулируй своими словами. Речь и картинка расходятся (кадр на переходе) — доверяй тому, что НА кадре.
3. **Расшифровка по ролям** — диалог, где видно, кто говорит.

**Честность по говорящим (важно, всегда соблюдай):**
- Если диаризация **не запускалась/упала** — пиши «реплики восстановлены по смыслу», не выдавай
  за разметку по голосу.
- Если диаризация прошла, но **шумная** (часто так: несколько человек в одной комнате на одном
  микрофоне → их не разделить; удалённый участник через сервис созвона отделяется лучше) — сведи
  метки к реальным людям по смыслу и **по роду глаголов** («выбрала», «зашла» → женщина), а в
  плашке «Как читать» честно опиши: кого отделили уверенно, а кого пишем общим «коллега».
- Никогда не приписывай конкретному человеку реплику, в которой не уверен, без оговорки.

## Заметки
- Всё считается **локально**; видео/аудио никуда не отправляются. Токен HF нужен только для
  разовой загрузки модели диаризации.
- Транскрипция идёт через faster-whisper с пословными таймкодами, диаризация — через pyannote
  напрямую (см. `scripts/diarize_transcribe.py`); медленное wav2vec2-выравнивание whisperx НЕ
  используется. Спикеры назначаются по перекрытию слов с речевыми интервалами pyannote.
- **Диаризация прожорлива по памяти и капризна. Запускай строго ОДИН процесс.** pyannote грузит
  весь файл сразу; на 16 ГБ RAM при паре свободных гигов на записи ~20+ мин её **убивает по OOM** —
  в логе при этом НЕТ трейсбэка, процесс просто исчезает (exit 137/144 = SIGKILL, не краш кода).
  Признак: текст распознался (есть «слов с таймкодами: N»), а на фазе «диаризация (pyannote)…»
  процесс умер. Лечение: не запускать второй прогон параллельно (две модели разом = гарантированный
  OOM), освободить память, гнать в один поток и ждать (фаза pyannote идёт после распознавания текста,
  на ней RSS ~1–3 ГБ). Если упала — честно скажи пользователю и предложи повтор или режим `plain`.
- **Качество диаризации зависит от записи.** Несколько человек в ОДНОЙ комнате на одном микрофоне
  pyannote не разделяет (даст «лишних» спикеров и порежет фразы); удалённый участник через сервис
  созвона (Pachka/Zoom) идёт отдельным каналом и отделяется лучше. Поэтому метки `SPEAKER_xx` почти
  всегда надо сводить к реальным людям вручную — по смыслу и роду глаголов (см. «Честность по
  говорящим»). `scripts/srt_to_dialogue.py` даёт черновик (склеивает реплики одного спикера).
- **PDF-отчёт собирается через pandoc + weasyprint** (brew; ставятся `scripts/setup.sh`). Скрипт
  `scripts/make_report.sh` делает markdown → автономный HTML (`--embed-resources` вшивает картинки
  base64) → PDF. Стили — `scripts/report.css`. weasyprint шумит warning'ами про `box-shadow`/`@media`
  — безобидно. Проверка: `mdls -name kMDItemNumberOfPages -raw OUT.pdf`.
- Модели скачиваются автоматически при первом запуске (кэш `~/.cache/huggingface`), поэтому
  первый прогон дольше. Модель Whisper по умолчанию `small` — на этой машине (Apple Silicon,
  ctranslate2 int8) только она работает с приемлемой скоростью (~0.17× реального времени) и при
  этом чисто распознаёт русский. Модели крупнее патологически медленные даже при свободной RAM:
  `medium` ≈ 32× реального времени, `large-v3-turbo` ≈ 4.5×. Менять смысла нет, пока не сменится
  окружение (GPU/оптимизированный билд ctranslate2). Переопределение: `WHISPER_MODEL=...`.
- YouTube требует куки браузера — `ingest.sh` по умолчанию берёт их из Chrome
  (`YTDLP_COOKIES_BROWSER=chrome|safari|firefox|none` для смены/отключения).
- **Извлечение кадров — «анализ → план», кадр в СЕРЕДИНЕ показа** (`extract.sh` + `plan_frames.awk`):
  карта смен сцены + тишины (без записи кадров), затем план — **середина каждого отрезка МЕЖДУ
  склейками** (а не в момент склейки!). Почему: кадр на склейке = середина перехода → смаз; а
  удержанные вставки (экран телефона/скринкаст между быстрыми склейками) на склейках теряются.
  Середина отрезка = стабильный показанный кадр, чёткий. Отрезки короче `MIN_SEG` (0.7с) —
  переходы, пропускаем. Извлекаем ЩЕДРО до `EXTRACT_MAX` (300); финальный отбор по СУТИ делают
  дальше `dedup_frames.py` (near-identical) + субагент-скринер по контактным листам (шаг 5b),
  режущие до `MAX_FRAMES` (80). Тюнинг: `EXTRACT_MAX`, `MAX_FRAMES`, `MIN_SEG`, `ANALYZE_THRESH`
  (0.1), `MAX_GAP_SEC` (45), `INFILL_STEP` (30), `SPEECH_RATIO` (0.3). Сводка → `$WORK/analysis.txt`.
  Полная логика отбора и обоснование — в `DESIGN_frame_selection.md`.
- **Формат кадров**: `FRAME_FORMAT=jpg|png` (по умолч. jpg). `png` — без потерь, для демо/скринкастов
  с мелким текстом UI (jpeg q3 его «мылит»); jpg — компактно, для говорящих голов. webp не поддержан
  (libwebp есть не во всех сборках ffmpeg, weasyprint/Read его не везде вшивают). Кадры получают
  расширение формата; оно же в `analysis.txt` (`frame_format=`) — при чтении/копировании кадров
  бери реальное расширение, не хардкодь `.jpg`.
